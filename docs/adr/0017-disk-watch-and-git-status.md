# 0017. Слежение за диском и статусы git - в главном процессе, цвета имён как в WebStorm

- **Статус:** Принято
- **Дата:** 2026-10-20

## Контекст

Владелец попросил красить имена в дереве по статусу git, как в WebStorm. Статус меняется
всё время: файлы правит Claude Code в панели рядом, правят в терминале, переключают
ветки. Дерево при этом читало папку один раз и не знало об изменениях на диске - это
висело открытым вопросом в `docs/architecture.md`. Цвет, который не обновляется, хуже,
чем никакого: он врёт.

## Варианты

**Окно спрашивает статус при открытии и при возврате фокуса.**

- Плюсы: ни одного нового механизма, только запрос.
- Минусы: правки Claude Code идут, пока окно в фокусе, - цвета и новые файлы в дереве
  отставали бы до следующего клика в другое приложение. Файлы, созданные снаружи, в
  дереве не появлялись бы вовсе.

**Опрашивать git status по таймеру.**

- Плюсы: просто.
- Минусы: процесс git каждые пару секунд на каждый открытый проект, даже когда ничего
  не меняется; и всё равно задержка до тика. Дерево это не чинит.

**Слежение за диском в главном процессе (fs.watch с recursive - на macOS это FSEvents),
статус git держит главный процесс и сам рассылает окну.**

- Плюсы: один поток событий на проект без обхода папок; дерево и цвета обновляются
  сразу после изменения. Статус - предметное состояние, его владелец - главный процесс
  (ADR 0003): чтения одного проекта идут по одному, и окно не путается в гонке ответов.
  Заодно шапка видит смену ветки в терминале без возврата фокуса.
- Минусы: новый долгоживущий механизм; при `pnpm install` событий тысячи - нужна пачка
  и предел. Чтение статуса само может трогать `.git` и будить слежение по кругу.

## Решение

Слежение в главном процессе. Только оно делает цвета и дерево правдой в ту же секунду,
а владение статусом у главного процесса - то же правило, что у проектов и веток. Цвета -
из темы WebStorm New UI Dark (`expUI_darkScheme.xml`), смешанные из нашей палитры:
изменён и переименован - синий, добавлен - зелёный, не в git - лососевый, игнорируется -
бурый, конфликт - красный. Папка, внутри которой есть изменения, - синяя (с конфликтом -
красная); удалённые файлы красят папку, но в дереве их нет.

## Факты и замеры

- `git status --porcelain=v2 -z --ignored=matching --untracked-files=normal`: 0,10 с на
  этом репозитории, 0,16 с на roas-radar и amazing-claude-code (M-серия, `time`).
  `--ignored=matching` отдаёт node_modules одной записью и внутрь не ходит.
- Из событий внутри `.git` важны только HEAD, индекс, ссылки, правила исключений,
  слияние и rebase, настройки, состояние подмодулей - белым списком. С включённым
  `core.fsmonitor` (scalar, большие монорепо) каждый git status пишет куки демона в
  `.git/fsmonitor--daemon/` - без белого списка статус перечитывался бы по кругу раз пять
  в секунду. Держит тест в `project-watcher.integration.test.ts` (с прежним отсевом по
  `objects` и `logs` он падает - проверено).
- Чтение статуса с `GIT_OPTIONAL_LOCKS=0` не переписывает индекс. Без этой переменной
  git status переписал индекс, увидев файл с новой датой и старым содержимым, - и
  слежение за `.git` разбудило бы следующее чтение. Держит тест
  `git-status.integration.test.ts` (без переменной он падает - проверено).
- Пачка событий уходит после 150 мс тишины, но не реже раза в секунду; больше 200 папок
  в пачке - окно перечитывает все папки проекта. Записей статуса больше 20 000 - статус
  обрезается, игнорируемые git выдаёт последними, они и пропадут.
- Слежение проверено на настоящем FSEvents (`project-watcher.integration.test.ts`): новый
  файл, коммит в терминале, проект - подпапка репозитория (`.git` выше корня). Вживую в
  копии окна: новый файл появился в дереве лососевым, папка над ним посинела, после
  удаления всё вернулось.

## Последствия

- Каналы - `shared/ipc/project-sync.contract.ts`: `git:getStatus`, события `fs:changed`
  (папки для перечитывания и «поменялся .git») и `git:status` (новый статус целиком).
  Окно пишет их в кэш React Query в `app/MainProcessSync`; строка дерева подписана только
  на свой статус.
- Код: `main/fs/project-watcher*.ts`, `watch-events.ts`, `watch-batch.ts` - слежение;
  `main/git/git-status*.ts` - чтение, разбор и сервис; связка - в `main/index.ts`.
- Статус читается, только если окно его спросило; закрытый проект перестаёт
  отслеживаться. Изменения только внутри игнорируемого (логи, сборки, node_modules)
  статус не будят: он от них не меняется, а пишут туда без перерыва. Место проекта в
  репозитории узнаётся заново только при вопросе окна и изменениях в `.git` - иначе
  одно чтение статуса - один процесс git.
- Переименованная папка перечитывается в окне со всем, что под ней: macOS сообщает
  только о ней самой, а кэш подпапок записан по старому месту. Так же - раскрытые
  папки-ссылки: macOS сообщает о настоящем пути цели, а не о ссылке.
- Проект - подпапка репозитория: кроме `.git` выше корня, без рекурсии слушаются папки
  между корнем репозитория и проектом - их `.gitignore` тоже красят файлы.
- Репозиторий без различия регистра (`core.ignorecase`, обычное дело на macOS) хранит
  ключи статуса в нижнем регистре, и окно ищет так же: git отдаёт путь с регистром из
  индекса, дерево - с диска, и папка, переименованная только регистром, иначе теряла бы
  цвета.
- Пропал сам проект (удалили, отключили диск) - дерево говорит, что папку не прочитать,
  а не показывает прежние файлы. Действия git из IDE по-прежнему сами перечитывают ветку, дерево и
  статус: итог человек ждёт сразу, а слежение сказало бы о том же чуть позже.
- Пересмотреть, если FSEvents начнёт терять события на огромных репозиториях или
  понадобится Linux/Windows: там recursive устроен иначе.
