# 0008. Процессор и память IDE: процессор от Electron, память от macOS через koffi

- **Статус:** Принято
- **Дата:** 2026-10-17

## Контекст

В строке состояния, рядом с версией, нужно в реальном времени показывать, сколько
процессора и памяти занимает сама IDE. Человек сверяет такие цифры с «Мониторингом
системы», поэтому они должны совпадать с ним, а не просто быть правдоподобными.

IDE - это несколько процессов: главный, окно, GPU, служебный сетевой. Считать надо
все вместе. Окно в песочнице и про процессы ничего не знает, значит, мерит главный
процесс (ADR 0003).

Процессор Electron отдаёт как надо: `app.getAppMetrics()` даёт по каждому процессу
среднюю загрузку с прошлого вызова, где 100% - одно ядро, как в «Мониторинге».
С памятью хуже: `memory.workingSetSize` на macOS - это RSS. В нём общие страницы
фреймворка Electron посчитаны в каждом процессе заново, и сумма выходит в три-четыре
раза больше настоящей. «Мониторинг системы» показывает физический след процесса
(`phys_footprint`), а его Electron для дочерних процессов не отдаёт.

## Варианты

**Сумма RSS из Electron.**

- Плюсы: ничего нового, одна строка.
- Минусы: цифра врёт в разы (замер ниже). Человек откроет «Мониторинг», увидит
  другое число и перестанет верить индикатору.

**Запускать `top` или `footprint` на каждый замер.**

- Плюсы: точная цифра без новых зависимостей.
- Минусы: `top -l 1` обходит все процессы машины - почти секунда и 0.8 с
  процессорного времени на каждый замер. Индикатор сам стал бы главным потребителем.

**`proc_pid_rusage` из libSystem через FFI-библиотеку koffi.** Системный вызов
отдаёт `phys_footprint` по pid своего же пользователя, прав сверх обычных не нужно.

- Плюсы: та же цифра, что в «Мониторинге», меньше миллисекунды на замер всех
  процессов. koffi - на Node-API, поэтому не пересобирается под каждую версию
  Electron, а готовый бинарник приходит отдельным пакетом под платформу.
- Минусы: первая нативная зависимость главного процесса. Бинарник должен лечь в
  `app.asar.unpacked` и подписаться вместе с бандлом; сам koffi грузится около 25 мс.

**Свой нативный аддон или вспомогательная программа на Swift.**

- Плюсы: без сторонней библиотеки.
- Минусы: свой шаг сборки (node-gyp и пересборка под Electron, или swiftc), своя
  подпись - больше движущихся частей, чем у готового koffi, ради одного вызова.

**Опрос или события.** Окно может спрашивать по таймеру (React Query
`refetchInterval`), а может главный процесс слать события. Загрузка процессора - это
среднее «с прошлого вызова», и опрос из окна задаёт этот интервал сам. Видимость
окна знает страница, поэтому скрытое окно просто не спрашивает, и главному процессу
не нужен таймер и учёт, смотрит ли кто-нибудь.

## Решение

Процессор - сумма `percentCPUUsage` из `app.getAppMetrics()`, память - сумма
`phys_footprint` через `proc_pid_rusage` и koffi. Окно спрашивает канал
`app:getResourceUsage` раз в секунду, пока его видно. Главная причина: только так
цифры совпадают с «Мониторингом системы» и при этом замер ничего не стоит.

## Факты и замеры

MacBook на Apple Silicon, Electron 44.7.2, koffi 3.3.3.

Голое окно Electron, сумма по четырём процессам:

| Процесс | RSS (`workingSetSize`) | `phys_footprint` (koffi) | `top`, столбец MEM |
| ------- | ---------------------- | ------------------------ | ------------------ |
| Главный | 146.2 МБ               | 42.4 МБ                  | 43 МБ              |
| GPU     | 64.9 МБ                | 19.4 МБ                  | 19 МБ              |
| Сетевой | 40.6 МБ                | 6.9 МБ                   | 6.9 МБ             |
| Окно    | 81.2 МБ                | 18.4 МБ                  | 18 МБ              |

`app.getAppMetrics()` и чтение следа всех четырёх процессов - 0.39 мс.
`require('koffi')` - 25.6 мс, `load` и `func` - 0.8 мс. `top -l 1 -pid 1` - 0.89 с,
из них 0.77 с системного времени.

Собранное приложение (`pnpm dist:local`): индикатор 149.1 МБ, сумма столбца MEM у
`top` по процессам той же копии - 148.7 МБ.

Повторить: запустить собранное приложение с `--remote-debugging-port=5316`, затем
`node apps/desktop/scripts/cdp.mjs eval "window.ide.invoke('app:getResourceUsage')"`
и сравнить с `top -l 1 -pid <pid> -stats pid,mem` по главному процессу и его детям.

## Последствия

- В главном процессе есть нативная зависимость. Она грузится при первом замере, а не
  на старте; не загрузилась - причина один раз уходит в журнал, а индикатор
  показывает только процессор. Проверка, что всё на месте, - тест
  `phys-footprint.integration.test.ts` на настоящем вызове.
- Скрипт установки koffi в `pnpm-workspace.yaml` выключен: он только перепроверяет
  готовый бинарник, а без него собирал бы из исходников CMake.
- `app.getAppMetrics()` зовёт только замер для строки состояния: интервал загрузки
  процессора у всех вызовов общий, второй вызывающий укоротит его первому.
- Следующий нативный вызов macOS, которого нет в Electron, делается так же, через
  koffi, без нового аддона.
- Пересмотреть, если Electron начнёт отдавать след дочерних процессов сам, или если
  IDE соберётся под Windows и Linux: там `proc_pid_rusage` нет.
