# 0009. GUI Claude Code: своя реализация на дизайн-системе, CLI - из главного процесса

- **Статус:** Принято
- **Дата:** 2026-10-17

## Контекст

Зона 7 (правая панель) - GUI провайдера LLM, первый провайдер - Claude Code. Готовый
GUI уже есть: панель amazing-claude-code (ACC) для JetBrains. Это интерфейс на React
(`webview/`, около 106 тысяч строк) и хост на Kotlin (около 85 тысяч строк), который
запускает CLI, держит процессы, разрешения, историю. Общаются они через
`__accSend` / `__accReceive`.

Один раз ACC уже копировали целиком - в claude-code-ide, и копия разошлась с
оригиналом: правки в одном месте не доезжали до другого. Поэтому вопрос «как
встраивать» был отложен до работы над зоной 7 (CLAUDE.md, правило 6).

Ограничения этой IDE: окно в песочнице и ходит в главный процесс только через
контракт IPC (ADR 0003); значения в стилях - только токены дизайн-системы, объёма
нет (ADR 0006); файлы не длиннее 200 строк `.tsx` и 300 строк `.ts`; фичи не видят
друг друга. Владелец продукта прямо попросил: GUI Claude Code должен быть собран из
наших компонентов и в нашей гамме, а не выглядеть чужой панелью.

## Варианты

**Панель ACC как есть в `<webview>` или `<iframe>`, хост на Node поверх её протокола.**

- Плюсы: сразу весь набор возможностей ACC.
- Минусы: чужая гамма, свои кнопки и меню внутри нашей панели - ровно то, чего
  владелец не хочет. Хост всё равно писать заново (Kotlin в Electron не запустится), а
  протокол панели заточен под JetBrains: Keymap, буферы редактора, десять языков.
  Второй стек стилей и вторая копия React в окне. Отдельная страница ослабляет
  песочницу: ей нужен свой мост.

**Общий пакет компонентов для ACC и IDE.**

- Плюсы: одна лента, один разбор протокола на два продукта.
- Минусы: у продуктов разные дизайн-системы, и общий пакет тянул бы одну из них в
  другой продукт. Релизы плагина и IDE оказываются связаны. ACC - монорепо со своим
  pnpm и TypeScript 7, IDE - TypeScript 6 (ADR 0002). Цена такой связки выше, чем
  экономия на ленте.

**Своя реализация в `features/claude-code`, CLI ведёт главный процесс.** ACC -
справочник по поведению и протоколу CLI, а не источник кода.

- Плюсы: собрано из примитивов `@amazing-ide/ui`, в гамме ADR 0006, по правилам
  границ и размеров. Состояние разговора у главного процесса, как у проектов и
  обновлений (ADR 0003): перезагрузка окна разговор не теряет. Ничего не копируется,
  значит, и расходиться нечему.
- Минусы: возможности ACC приходится собирать заново, паритет растёт постепенно.
  Знание о протоколе CLI живёт в двух местах (Kotlin в ACC и TypeScript здесь).

## Решение

Своя реализация. Главный процесс (`main/claude/`) запускает `claude` в режиме
`stream-json`, разбирает поток в ленту и держит разговоры; окно (`features/claude-code`)
зеркалит их в кэше React Query и рисует нашими компонентами. Главная причина: GUI
должен быть частью этой IDE по виду и по устройству, а оба других варианта либо
приносят чужой интерфейс, либо связывают два продукта с разными дизайн-системами.

## Факты и замеры

Протокол проверен вживую на Claude Code 2.1.293 (модель haiku, пробник на Node):

- Запуск: `claude -p --input-format stream-json --output-format stream-json --verbose
--include-partial-messages --permission-prompt-tool stdio`. Без
  `--permission-prompt-tool stdio` всё, что требует разрешения, CLI молча отклоняет
  (`system/permission_denied`).
- Вопрос разрешения приходит строкой `control_request` с `subtype: can_use_tool`
  (имя инструмента, вход, `permission_suggestions`, `tool_use_id`), ответ -
  `control_response` с `behavior: allow` и `updatedInput` или `behavior: deny` и
  `message`. Проверено: после ответа `allow` файл создан.
- В `system/init` - модель, режим разрешений, `slash_commands`; полный список команд с
  описаниями приходит отдельно, в `system/commands_changed`. Окно контекста - в
  `result.modelUsage.<модель>.contextWindow`, цена хода - `total_cost_usd`.
- Результат инструмента приходит дважды: текстом в `tool_result` и структурой в
  `tool_use_result` (у Bash - stdout и stderr, у Edit и Write - `structuredPatch`).
  Лента берёт структуру, где она есть.
- Размышления у текущих моделей приходят пустым блоком `thinking` с подписью; сколько
  их было, CLI сообщает отдельно (`system/thinking_tokens`).

Повтор: `printf '%s\n' '{"type":"user","message":{"role":"user","content":[{"type":"text","text":"hi"}]}}' | claude -p --input-format stream-json --output-format stream-json --verbose --model haiku`.

Замера производительности ленты на длинных разговорах пока нет.

## Последствия

- Предметные данные Claude Code (разговоры, лента, вопросы разрешения) принадлежат
  главному процессу. Окно получает их запросом и событиями `claude:*` и держит в
  кэше React Query. Интерфейсное (черновик в поле, раскрытые карточки) - в окне.
- Разбор потока CLI в ленту - чистые функции в `main/claude/feed/` с тестами. Окно
  разбора не делает: оно рисует готовые элементы ленты из `shared/claude-feed.ts`.
- С `-p` CLI не спрашивает, доверяешь ли ты папке, и сразу читает её настройки, хуки
  и CLAUDE.md, а хук выполнит любую команду. Поэтому спрашивает панель: папка
  доверена, если человек согласился в панели или раньше в терминальном Claude Code
  (`hasTrustDialogAccepted` в `~/.claude.json`, для папки или её родителя). Пока не
  доверена, процесс не поднимается.
- Сообщение не теряется, если разговор не может начаться (папке не доверились, CLI
  нет, папку проекта удалили): оно встаёт в очередь, переживает перезапуск IDE и
  уходит первым, когда причина снята. Очередь сама не отвечает на вопросы CLI: пока
  висит вопрос, она ждёт.
- Режим разрешений новой вкладки берётся из настроек Claude Code, но не из любых:
  проект может выбрать только «спрашивать», «принимать правки» и «план». «Без
  вопросов» - только из настроек человека и если нигде не запрещено, «авто» - из
  настроек человека или организации. Иначе чужой репозиторий включил бы себе свободу
  сам.
- Процессы CLI - дети IDE, и команды `!`, и разовые команды CLI тоже: каждый живёт в
  своей группе процессов, все учтены в одном месте (`cli/process-group.ts`). Выход
  ждёт, пока они закроются (на практике меньше секунды, потолок - 5 секунд), и
  добивает упрямых, а не бросает их сиротами вместе с MCP-серверами.
- Сообщение человека уходит в CLI под нашим uuid: CLI берёт его за имя строки
  транскрипта, и по нему сообщение откатывается (`rewind_conversation`,
  `rewind_files` - копии файлов CLI ведёт только с
  `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING`) и форкается (`--fork-session
--session-id --resume-session-at`, проверено на 2.1.293). Отрезанное откатом CLI из
  файла не вырезает - это делает чтение транскрипта (`history/transcript-rewinds.ts`).
- Команды `!` выполняет панель, а не агент: ход модели и вопрос о разрешении на «git
  status» не нужны. Модель видит команду и вывод в следующем сообщении, теми же
  метками, что ставит терминальный Claude Code.
- Аккаунт - отдельное хранилище входа CLI, а не отдельная папка настроек: с
  `CLAUDE_CONFIG_DIR` у аккаунта были бы свои транскрипты, история, MCP и плагины.
  Переменная хранилища у обычного входа удаляется, даже унаследованная из терминала:
  IDE, запущенная из ACC, иначе тихо шла бы на его аккаунт. Хранилища
  amazing-claude-code берутся как есть и никогда не удаляются отсюда. Голосовой ввод
  из ACC не переносится - так решил владелец.
- Кто вошёл в аккаунт, говорит само хранилище, а не общий `~/.claude.json`: тот
  называет того, чей процесс писал его последним. Процесс CLI поднимается в пустом
  своём конфиге (`CLAUDE_CONFIG_DIR` - только для этого вопроса, никогда для
  разговора), отвечает на `get_usage` и пишет профиль с сервера в этот конфиг.
  Проверено на 2.1.293: `auth status` в пустом конфиге почту не называет, а после
  `get_usage` профиль на месте через секунду.
- Лимиты подписки - ответ CLI на `get_usage`, по аккаунту. Текущий аккаунт после
  каждого хода спрашивается у живого разговора (CLI знает расход из заголовков ответов
  модели), остальные и простаивающий текущий - своим процессом CLI в постоянной папке
  конфига аккаунта. Папка постоянная ради кэша CLI: сервер отбивает частые вопросы про
  один аккаунт (429, замер на 2.1.293 - после четвёртого вопроса за несколько минут),
  CLI потом пять минут не спрашивает и отвечает цифрами из кэша этого же аккаунта. В
  пустой временной папке ответ был бы пустым - так и выглядел первый замер, по которому
  лимиты сочли недоступными. Каждый аккаунт спрашивается не чаще раза в две минуты,
  живой разговор - раза в 20 секунд; из двух ответов остаётся снятый с сервера позже.
- Экраны MCP и плагинов запускают CLI в папке проекта только после доверия к ней, как
  и разговор: CLI там читает настройки проекта. Своё для всех проектов (область user,
  маркетплейсы) идёт из домашней папки. Адреса, аргументы и текст CLI уходят в окно
  без ключей (`tools/secret-mask.ts`), адрес входа в MCP-сервер открывается, только
  если это сайт.
- Разметка ответа - лексер `marked` и свой рендер в React-элементы, без
  `innerHTML`. Подсветка кода - shiki с движком регулярных выражений на JS (WASM
  потребовал бы ослабить CSP окна), цвета - роли `--color-syntax-*` из токенов. Их же
  потом возьмёт тема Monaco (ADR 0005).
- Плавное появление ответа - `smooth-stream-text`: поток CLI приходит рывками.
- Правило 6 в CLAUDE.md теперь звучит так: код ACC не копируется, поведение и протокол
  берутся из него как из справочника.
- Пересмотреть, если появится второй продукт на этой же дизайн-системе, которому
  нужна та же лента: тогда лента может уехать в общий пакет.
