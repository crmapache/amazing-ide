# 0019. Просмотр Markdown: три вида как в WebStorm, HTML файла - элементами React по списку GitHub

- **Статус:** Принято
- **Дата:** 2026-10-20

## Контекст

Владелец открыл README в редакторе и не нашёл того, к чему привык в WebStorm: справа над
файлом Markdown три кнопки - только код, код и просмотр рядом, только просмотр. Нужен
просмотр, похожий на GitHub: заголовки, таблицы, списки дел, блоки кода с подсветкой,
картинки (значки с сайтов и скриншоты из репозитория), ссылки на другие файлы и разделы,
HTML, которым пишут README (`<p align="center">`, `<details>`, `<kbd>`).

Ограничение одно и жёсткое: просмотр стоит в странице окна, а у страницы есть мост в
главный процесс (`window.ide`), то есть запись файлов, git, запуск CLI. README - чужой
текст из репозитория. Если HTML из него исполнит хоть строчку, это строчка с правами IDE.

В ленте Claude Code уже есть свой Markdown (`features/claude-code/Markdown`): разбор marked,
отрисовка своими элементами React, HTML показывается текстом.

## Варианты

**Взять Markdown ленты Claude Code.**

- Плюсы: уже есть, без innerHTML, стили готовы.
- Минусы: сделан для чата - заборы кода по правилу ACC, заголовки не крупнее h3 для узкой
  панели, тире вместо точек в списках, HTML текстом. README с HTML выглядел бы сломанным,
  картинок и ссылок на файлы нет. Чтобы стать документом, ему пришлось бы раздвоиться
  внутри, а фичи друг друга не видят - его пришлось бы ещё и вынести из `claude-code`.

**marked в HTML-строку, очистка DOMPurify, innerHTML.**

- Плюсы: так делает большинство просмотров, HTML файла рисуется браузером как есть.
- Минусы: безопасность держится на одном очистителе и на том, что его вызвали везде.
  Ошибка в нём или в нашем вызове - и код из README исполняется со всеми правами окна.
  Ссылки и картинки всё равно пришлось бы перехватывать после вставки.

**Отдельный `<iframe sandbox>` или webview со своей страницей.**

- Плюсы: даже исполненный скрипт заперт без доступа к мосту.
- Минусы: своя страница со своими стилями (токены и шрифты - второй раз), прокрутка с
  кодом и переход по ссылке на файл - через сообщения между окнами. У `srcdoc` CSP
  наследуется от окна, так что картинки из проекта всё равно не грузятся без своей схемы
  или IPC. Много движущихся частей ради того, что решается проще.

**marked в HTML-строку, разбор браузером в отдельный документ, сборка элементов React по
списку GitHub.**

- Плюсы: документ из `DOMParser` - без окна: скрипты не исполняются, картинки не
  грузятся, обработчики не вызываются. В страницу идёт только собранное по списку тегов
  и атрибутов, строкой HTML не идёт ничего - React экранирует текст сам. Разбор HTML -
  браузерный, поэтому HTML, разорванный абзацами (`<details>` с Markdown внутри),
  собирается правильно. Ссылка, картинка, блок кода и пункт-дело - свои компоненты.
- Минусы: список тегов и атрибутов надо держать самим, и HTML вне списка (видео, svg,
  формы) не рисуется. Каждая перерисовка строит дерево заново.

## Решение

Последний вариант. Главная причина: безопасность не зависит от того, не ошибся ли
очиститель, - в окно попадают только элементы, которые мы собрали сами из разрешённого,
а разобранный документ ничего не исполняет. Просмотр при этом GitHub-подобный: HTML
README рисуется. Три вида - как в WebStorm, кнопками в правом верхнем углу файла; рядом -
прокрутка вместе с кодом, как в VS Code.

## Факты и замеры

MacBook Pro M1 Pro. Разбор Markdown (marked, в Node - тот же V8) и сборка элементов из
HTML (happy-dom в тестах - медленнее Chromium) - медианы 15 прогонов:

| Файл                                        | marked | HTML → элементы (happy-dom) |
| ------------------------------------------- | ------ | --------------------------- |
| `docs/architecture.md`, 241 строка          | 1,5 мс | 6,1 мс                      |
| Сгенерированный, 5 500 строк (500 разделов) | 9,9 мс | 152 мс                      |

Тот же сгенерированный файл в окне копии (`agent-window.sh`): `DOMParser` и обход
готового листа просмотра (657 КБ HTML, 23 500 узлов) - 25 мс в Chromium. Задержку от
нажатия до перерисовки в копии честно не измерить: окно в фоне, Chromium придерживает
в нём кадры и таймеры (тот же эффект, что в ADR 0018).

Перерисовка ждёт паузу в наборе 120 мс, так что на обычных документах (сотни строк)
просмотр успевает за набором с запасом.

Безопасность держат тесты `markdown-dom.utils.test.ts` (на настоящем разборщике HTML):
`<script>`, `<style>`, `<iframe>`, `<form>`, `<svg>` уходят вместе с содержимым,
обработчики, стили, классы и `data-*` снимаются, `javascript:` и `file:` в ссылке - никуда,
id из файла - с приставкой.

## Последствия

- Вид - `features/editor/markdown-layout.store.ts`: у файла - выбранный на нём, у нового -
  выбранный последним (помнится между запусками, как и доля ширины под код). Сначала -
  только код, как было. Переход к строке (поиск, лента) в файле, открытом одним
  просмотром, ставит код рядом.
- Кнопки вида - плавающая панель в правом верхнем углу файла, над кодом или просмотром
  (`MarkdownLayoutSwitch`): приглушена, чтобы читать текст под ней, под курсором и с фокусом -
  в полную силу. Сначала они стояли справа в полосе вкладок, но колонка только у Markdown
  меняла ширину полосы, и на каждом переходе между вкладками те переезжали между рядами.
  Полоса о картинках с сайтов оставляет справа место под панель (`_layout-switch.scss`).
- Разбор - `markdown-html.utils.ts` (GFM, шапка YAML - блоком кода, метка строки перед
  каждым блоком), сборка - `markdown-dom.utils.ts`, список - `markdown-preview.constants.ts`.
  Новый тег или атрибут - строка в списке и тест на то, что пускаем.
- Картинка проекта - `fs:readImage` (`main/fs/image-file.ts`): только картинка по
  расширению настоящего файла (ссылка `logo.png` на `.env` - не картинка), только внутри
  проекта, до 20 МБ, data URL. Отказ - видом (нет, не картинка, велика, нельзя прочесть),
  просмотр пишет причину на месте картинки. Окно присылает версию, которую держит: тот же
  файл отвечает unchanged без байтов - пачка изменений диска не гоняет картинки заново.
- Картинки с сайтов - только по нажатию «Show» над просмотром и только те адреса, что в
  файле в этот момент (`web-images.store.ts`). Причина - агент рядом: поймав чужую
  инструкцию, он мог бы вписать в открытый README картинку с секретом в адресе, и окно
  само отправило бы его наружу, в обход разрешений Claude Code на сеть. Новый адрес
  после правки снова ждёт нажатия. Грузит главный процесс (`main/preview/web-image.ts`):
  свой сеанс в памяти без cookies, только https (и после переадресации), только ответ
  image/…, до 10 МБ, срок 15 с. CSP окна остаётся `img-src 'self' data:` - окно в сеть не
  ходит вовсе. Сертификат клиента IDE не предъявляет никому (`select-client-certificate`).
- Ссылка: сайт - в браузер (как в ленте, через `openExternalWeb`), `#раздел` - к
  заголовку, `#` и `#top` - наверх, путь - общим действием «открыть файл», как из ленты
  (файл во вкладке и в дереве, `#L10` - на строку, папка - в дереве), но точным путём:
  битая ссылка не откроет одноимённый файл из другой папки (`fs:locatePath` с `exact`).
  Ссылка на картинку проекта открывает её крупно (`Lightbox`). Остальные схемы - текст.
  Страница окна по ссылке не уходит: нажатие перехватывается.
- Прокрутка вместе - `markdown-scroll.hooks.ts`: между метками строк по доле, ведёт тот,
  кого крутит человек. Monaco сообщает о прокрутке прямо внутри `setScrollTop`, поэтому
  своя прокрутка редактора помечается флагом, а не сверкой позиции: иначе лист,
  округлённый редактором до целой строки, откатывался бы назад над высокой картинкой.
  Метка - на уровне блоков: внутри длинного списка или таблицы прокрутка идёт по доле.
- Раскраска кода общая с лентой: `lib/syntax-classes.utils.ts`, `lib/_syntax-roles.scss`,
  `lib/highlighter.hooks.ts`.
- Формулы, диаграммы mermaid, видео и svg в просмотре не рисуются (mermaid - блоком кода).
- Пересмотреть, если документы на десятки тысяч строк станут обычным делом и перерисовка
  целиком перестанет успевать (перерисовывать только изменившиеся блоки), или если
  понадобится HTML вне списка GitHub.
