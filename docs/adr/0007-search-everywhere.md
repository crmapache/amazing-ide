# 0007. Поиск везде: файлы и текст через git, сравнение имён в окне

- **Статус:** Принято
- **Дата:** 2026-10-17

## Контекст

Нужен поиск как Search Everywhere в WebStorm: кнопка с лупой в шапке и двойной
Shift, вкладки, поле, список под ним. Отдельный вид «Поиск» в левой панели убран: он
дублировал бы шапку.

Чем искать сейчас, без разбора кода: файлы по имени, действия IDE (то, что уже есть
в меню проекта и ветки, раскладка панелей) и текст в файлах. Классы и символы требуют
разбора кода, а редактора ещё нет (Monaco, [ADR 0005](0005-editor-engine.md)), поэтому
вкладок Classes и Symbols нет вовсе, а не пустые заглушки.

Ограничения: окно не ходит в файловую систему (только через IPC, ADR 0003), в
проектах почти всегда есть git, и он уже нужен IDE (ветки, pull, push). Игнорируемое
в `.gitignore` (node_modules, сборки) искать нельзя: и шум, и медленно.

## Варианты

**Список файлов и поиск текста через git, запасной обход для папок без git.**
`git ls-files --cached --others --exclude-standard` и `git grep --untracked`.

- Плюсы: `.gitignore` учитывается сам, git grep быстрый (C, несколько потоков),
  ничего нового в сборку не едет.
- Минусы: два пути кода - для папки без git свой обход с жёстким списком тяжёлых
  папок вместо `.gitignore`.

**ripgrep в составе приложения** (`@vscode/ripgrep`, как VS Code).

- Плюсы: один путь для любой папки, быстрее всех на больших проектах.
- Минусы: бинарник качается из GitHub на установке (у Electron 43+ такое уже
  ломалось, свой скрипт установки), его надо распаковывать из asar и подписывать -
  это правка сборки и проверка самообновления ради выигрыша, которого на наших
  проектах не видно.

**Свой обход и поиск на Node везде** (плюс разбор `.gitignore` библиотекой).

- Плюсы: никаких внешних программ.
- Минусы: поиск текста читает весь проект на каждый запрос в главном процессе, на
  большом проекте это секунды и занятый процесс.

**Где сравнивать имена файлов:** в окне по загруженному один раз списку или в главном
процессе на каждую букву через IPC. В окне - без задержки IPC на букву и без
состояния поиска в главном процессе; цена - список путей один раз на открытие.

## Решение

Git и запасной обход для папок без git; список файлов загружается в окно один раз на
открытие поиска, имена сравниваются там же нечётким сравнением, как в WebStorm
(буквы по порядку, выше куски целиком, начала слов и заглавные). Текст ищет главный
процесс после паузы в наборе, новый поиск отменяет старый. Главная причина: git уже
есть и уже знает, что игнорировать, а замеры ниже показывают запас по скорости.

## Факты и замеры

MacBook на Apple Silicon, git 2.50.1. Время - `/usr/bin/time -p`:

| Проект              | Файлов | ls-files | grep «function» | grep без совпадений |
| ------------------- | ------ | -------- | --------------- | ------------------- |
| miestimado          | 2 646  | 0.08 с   | 0.31 с          | 0.32 с              |
| /opt/homebrew (tap) | 3 172  | 0.10 с   | 0.66 с          | 0.28 с              |

Сравнение имён в окне (vitest, 50 000 синтетических путей): разбор списка один раз -
около 30 мс, ранжирование на букву - 8-30 мс в зависимости от запроса. Набор не
тормозит: запрос к спискам идёт через `useDeferredValue`.

Повтор: `git -C <проект> ls-files --cached --others --exclude-standard -z`,
`git -C <проект> grep --untracked -n -I -i -F -z -e <текст> -- .`.

На этом репозитории в главном процессе: список файлов - около 40 мс, поиск текста -
50-160 мс (в том числе с упором в предел совпадений), обход папки без git - 35-60 мс.

Пределы: 50 000 путей в списке, 500 совпадений текста и не больше 20 на файл, около
8 секунд на поиск текста. Упёрлись - показывается найденное с пометкой «не всё».

Грабли, найденные по пути:

- В локали C, которую IDE ставит git для разбора вывода, `git grep -i` складывает
  регистр только у латиницы: «ПРИВЕТ» не находит «привет». Для grep - UTF-8.
- Личные настройки git (`grep.fullName`, `grep.column`) меняют формат вывода -
  передаются `--no-full-name --no-column`.
- Предел на файл (`--max-count`) - git 2.38 и новее. На старом git (код 129) поиск
  повторяется без него; любой другой сбой grep в репозитории - чтение по списку
  `git ls-files`, а не обход диска: обход не знает `.gitignore` и нашёл бы `.env`.
- Finder пишет имена в NFD («й» - буква и значок отдельно), git отдаёт NFC, с
  клавиатуры приходит NFC. Все пути, которые уходят в окно (список файлов, поиск,
  дерево), главный процесс приводит к NFC - иначе файл не находится, а найденный не
  раскрывается в дереве.
- Без git поиск текста не читает файлы по символическим ссылкам, как и git grep:
  ссылка могла вести за пределы проекта.
- Строка из git grep держится не длиннее 64 КБ: однострочный бандл в десятки
  мегабайт иначе разбирался бы целиком.
- Pull, запущенный из меню, и checkout из поиска шли одновременно: fetch внутри pull
  долгий и не держит `index.lock`, и pull потом перематывал уже новый HEAD.
  Записывающие команды git теперь в очереди на проект (`main/git/git-write-queue.ts`),
  а окно не предлагает действий git, пока идёт pull.

## Последствия

- Каналы `search:listFiles` и `search:findText`, код - `main/search/`, окно -
  `features/search-everywhere/`. Действия IDE собирает `workbench/actions/`: им нужны
  сразу проекты, git и раскладка.
- Диалоги клонирования и git открываются из любого места: их состояние живёт в
  сторах фич (`projects.store.ts`, `git-dialogs.store.ts`), а не внутри кнопок.
- Новый примитив `ListBox` - список под полем поиска, где фокус остаётся в поле.
  Меню (`Menu`) для этого не годится: оно уводит фокус в пункты.
- Кнопки с лупой в шапке больше нет (2026-10-20, решение владельца: шапка без кнопок
  справа). Поиск открывается двойным Shift и сочетаниями вкладок, панель стоит сверху
  по центру окна, как и раньше. Живёт он в своём слое `workbench/SearchLayer`, а не в
  шапке.
- Пересмотреть: проекты на сотни тысяч файлов (тогда ripgrep или индекс в главном
  процессе со слежением за диском) и появление разбора кода (вкладки Classes и
  Symbols, поиск по ним - отдельное решение).
